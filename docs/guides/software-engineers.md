# For software engineers moving into ML

You already know APIs, typing, testing, and CI. What's usually missing is
knowing what the ML lifecycle *requires* — and tooling that speaks your
idiom. `mlops-toolbox` maps ML concerns onto workflows you already trust.

## Start from a scaffold

```bash
mt init my-model
```

You get a typed training entry point, a `.github/workflows/model-ci.yml`
that trains and gates on every PR, and a README. The scaffold is the
lifecycle checklist in executable form.

## Model quality as a failing check

`mt gate` turns evaluation metrics into exit codes — the same contract as a
test suite:

```yaml
# .github/workflows/model-ci.yml (generated by mt init)
- name: Train and register
  run: python train.py
- name: Quality gate
  run: mt gate "accuracy>=0.85" "f1_macro>=0.8" --model my-model --tracking-uri sqlite:///mlops.db
- name: Lifecycle audit
  run: mt doctor --tracking-uri sqlite:///mlops.db
```

A model that regresses below threshold fails the PR. `mt doctor` fails the
build when a lifecycle stage is missing (no contract, no drift baseline...),
with a hint naming the fix.

## Let the doctor teach the lifecycle

Run `mt doctor` against any project and read the failing checks — each hint
is the next thing to learn, in order. See [Lifecycle
health](../concepts/lifecycle-health.md).

## Everything is typed

The public API is `mypy --strict`-clean and built on pydantic. Contracts,
reports, and results are all typed models — your editor autocompletes them,
and your own strict-mypy code composes with them without `# type: ignore`.

## Scheduled monitoring is just cron + exit codes

```bash
# nightly cron / scheduled CI job
mt drift my-model --input todays_data.parquet || notify-team
```

`mt drift` exits `1` when drift is detected — wire it to whatever alerting
you already run.
